# Directory role assignment: AzureAD research for issue #4894, ask 2

Research date: 2026-11-18. HashiCorp `main` resolved through GitHub's commits API to [`e4bf321593a89f1363ef6ebe457f5843b8046882`](https://github.com/hashicorp/terraform-provider-azuread/commit/e4bf321593a89f1363ef6ebe457f5843b8046882), committed 2026-11-18 15:21:50 UTC. ## Endpoint and identity semantics

- **Verified Graph beta:** use `/beta/roleManagement/directory/roleAssignments`, representing one role definition assigned to one principal at one scope. Supported principals are users, **role-assignable** groups, and service principals. The resource exposes create/list/get/delete, with no update method. Treat assignment changes as replacement. [`unifiedRoleAssignment` beta](https://learn.microsoft.com/en-us/graph/api/resources/unifiedroleassignment?view=graph-rest-beta).
- **AzureAD:** the assignment resource uses the unified endpoint through its stable SDK; the vendored client version explicitly selects `v1.0`. This is its implementation choice, not a beta limitation. [Assignment create](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-azure-sdk/microsoft-graph/rolemanagement/stable/directoryroleassignment/method_createdirectoryroleassignment.go#L50-L64), [version](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-azure-sdk/microsoft-graph/rolemanagement/stable/directoryroleassignment/version.go#L6).
- **Legacy distinction:** `azuread_directory_role_member` uses role membership references, with a `role_object_id`, role-level lock, existing-member check, and import-as-existing diagnostic. Its API is `POST /directoryRoles/{role-id}/members/$ref`; Microsoft recommends unified RBAC instead. Do not transplant those membership IDs or duplicate-check behavior into the new resource. [Legacy resource](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_member_resource.go#L81-L129), [beta membership API](https://learn.microsoft.com/en-us/graph/api/directoryrole-post-members?view=graph-rest-beta).
- **Role IDs:** Graph create accepts the service-wide built-in template ID or directory-specific **role definition** ID as `roleDefinitionId`. An activated `directoryRole.id` is a different identity. AzureAD's examples correctly use `azuread_directory_role.template_id` for built-ins and `azuread_custom_directory_role.object_id` for custom definitions. Its generic schema description saying “directory role object ID” is misleading. [Graph create example 1](https://learn.microsoft.com/en-us/graph/api/rbacapplication-post-roleassignments?view=graph-rest-beta#example-1-create-a-role-assignment-with-tenant-scope), [AzureAD examples](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/docs/resources/directory_role_assignment.md#L19-L61), [activated-role state mapping](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_resource.go#L224-L226).
- **Scopes:** actual property names are `directoryScopeId` and `appScopeId`, not `applicationScopeId`. `/` means tenant scope; directory scopes can also identify administrative units, application objects, or attribute sets. An application-object directory scope is `/{application-object-id}`, not an application/client ID. `appScopeId` represents resource-application-defined scopes; the documented catalog example belongs to entitlement management. Do not infer directory-provider support from that example. [Graph beta create body](https://learn.microsoft.com/en-us/graph/api/rbacapplication-post-roleassignments?view=graph-rest-beta#request-body), [AzureAD application-scope fixture](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_assignment_resource_test.go#L212-L235).

## AzureAD schema, lifecycle, and IDs

All attributes below are strings; every configurable attribute has `ForceNew`. There is no Update callback. Create/read/delete each default to five minutes. [Schema and callbacks](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_assignment_resource.go#L25-L94).

| AzureAD attribute | Requirement | Validation / behavior |
| --- | --- | --- |
| `role_id` | Required | UUID; sent directly as `roleDefinitionId` |
| `principal_object_id` | Required | UUID; sent as `principalId` |
| `app_scope_id` | Optional + computed | Nonempty if supplied; conflicts with directory scope |
| `directory_scope_id` | Optional + computed | Nonempty if supplied; conflicts with app scope |
| Terraform `id` | State identity | Assignment path described below |

Create chooses app scope, otherwise explicit directory scope, otherwise `/`. It POSTs directly: **no duplicate preflight, adoption, role activation, principal lookup, or custom POST retry predicate**. A nil response/ID fails. It saves the ID before polling GET until three consecutive successes, at least one second apart; polling 404 means pending. Read GET 404 removes state; other failures remain errors. Read hydrates all four attributes. Delete calls DELETE once through SDK retries, with **no explicit 404 suppression or deletion waiter**. [Lifecycle](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_assignment_resource.go#L97-L207).

Current import/state ID is **`/roleManagement/directory/roleAssignments/{assignment-id}`**, case-sensitive in the standard parser. Its final segment is user-specified, not UUID-validated. The importer validates then passes state through. The v0 state migration wraps the old bare ID. The current documentation's bare-ID import example is stale, independently reported in upstream #1742. [Parser and formatter](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-azure-sdk/microsoft-graph/common-types/stable/id_rolemanagementdirectoryroleassignment.go#L27-L98), [import helper](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/helpers/tf/pluginsdk/imports.go#L17-L45), [migration](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/migrations/directory_role_assignment_resource.go#L46-L51), [incorrect example](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/docs/resources/directory_role_assignment.md#L111-L117), [#1742](https://github.com/hashicorp/terraform-provider-azuread/issues/1742).

The assignment ID is **opaque**: Graph examples include URL-safe encoded IDs ending `-1`. Do not derive it from principal/role IDs or validate it as a UUID. To discover existing IDs, LIST assignments; beta supports `$filter`, `$select`, `$expand`, including filtering role definition and principal. A proposed duplicate check must additionally compare scope and follow pagination. [Graph get](https://learn.microsoft.com/en-us/graph/api/unifiedroleassignment-get?view=graph-rest-beta), [Graph list](https://learn.microsoft.com/en-us/graph/api/rbacapplication-list-roleassignments?view=graph-rest-beta), [filterable properties](https://learn.microsoft.com/en-us/graph/api/resources/unifiedroleassignment?view=graph-rest-beta#properties).

## HTTP behavior, permissions, and consistency

| Operation, all under `/beta` | Official successful result | Application permission |
| --- | --- | --- |
| `POST /roleManagement/directory/roleAssignments` | `201 Created` + assignment including `id` | `RoleManagement.ReadWrite.Directory` |
| `GET /roleManagement/directory/roleAssignments/{id}` | `200 OK` + assignment | `RoleManagement.Read.Directory` least privileged; write permission also accepted |
| `GET /roleManagement/directory/roleAssignments` | `200 OK` + collection | Same read/write options |
| `DELETE /roleManagement/directory/roleAssignments/{id}` | `204 No Content`, no body | `RoleManagement.ReadWrite.Directory` |

Sources: [beta create](https://learn.microsoft.com/en-us/graph/api/rbacapplication-post-roleassignments?view=graph-rest-beta), [get](https://learn.microsoft.com/en-us/graph/api/unifiedroleassignment-get?view=graph-rest-beta), [list](https://learn.microsoft.com/en-us/graph/api/rbacapplication-list-roleassignments?view=graph-rest-beta), [delete](https://learn.microsoft.com/en-us/graph/api/unifiedroleassignment-delete?view=graph-rest-beta). Delegated write additionally requires a supported signed-in-user role; Privileged Role Administrator is least privileged. AzureAD docs also list `Directory.ReadWrite.All` for app-only writes, but current Graph beta create/delete tables do **not** list it: document the verified `RoleManagement.ReadWrite.Directory` permission instead. [AzureAD permissions claim](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/docs/resources/directory_role_assignment.md#L9-L15).

AzureAD's generated SDK accepts wider status sets (POST 200/201/202/204; DELETE 200/204; GET 200), but these are SDK tolerances, not promised Graph responses. It still needs a POST response ID. [Generated POST](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-azure-sdk/microsoft-graph/rolemanagement/stable/directoryroleassignment/method_createdirectoryroleassignment.go#L50-L89), [DELETE](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-azure-sdk/microsoft-graph/rolemanagement/stable/directoryroleassignment/method_deletedirectoryroleassignment.go#L53-L80).

Shared SDK HTTP handling retries 408/424, delegates 429 and server failures to `go-retryablehttp`, honors numeric `Retry-After`, and otherwise uses exponential backoff from 1 to 61 seconds with retry count bounded by context deadline. The default policy excludes 501. It does not make ordinary assignment POST 404 retryable. [SDK execution](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-azure-sdk/sdk/client/client.go#L446-L486), [backoff](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-azure-sdk/sdk/client/client.go#L673-L724), [retry policy](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/vendor/github.com/hashicorp/go-retryablehttp/client.go#L495-L541).

The reviewed official CRUD docs do not specify a duplicate-assignment HTTP status/error code or a visibility SLA. Do not promise 409, borrow app-role/PIM error strings, retry every 400, or silently adopt an existing assignment based on these sources. AzureAD's post-create waiter is implementation evidence of eventual consistency, not an API latency guarantee.

## Tests, bug history, and implementation lessons

AzureAD acceptance tests cover user/service-principal assignments for built-in/custom roles, application-scoped service principals, imports, and adding then removing a second user's assignment without deleting the first. They check remote existence and UUID role/principal fields. They do **not** cover role-assignable groups, duplicate creation, missing-object deletion, waiter failures, or explicit tenant-scope assertions. [Tests](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_assignment_resource_test.go#L23-L164), [fixtures](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_assignment_resource_test.go#L193-L295).

Relevant history:

- [Initial resource #826](https://github.com/hashicorp/terraform-provider-azuread/pull/826) introduced unified assignments for built-in/custom roles and scopes, replacing the membership resource.
- [Scope fix `031f18e`](https://github.com/hashicorp/terraform-provider-azuread/commit/031f18eab5bae5a403c94c269e83ad3d017d0db7) corrected path scope validation and made role/principal required; [`8fea870`](https://github.com/hashicorp/terraform-provider-azuread/commit/8fea8706e7e81524c55e915c09e921eeec41b582) restored `/` when scope is omitted. Scope values are paths, not UUIDs.
- [Typed ID migration `51dd455`](https://github.com/hashicorp/terraform-provider-azuread/commit/51dd4555904e7748a121115eb37e04b077ae8288) changed state/import identity to a full path. [Follow-up `b384118`](https://github.com/hashicorp/terraform-provider-azuread/commit/b384118236bd20205adf87eff214dadc5f9a8bae) removed erroneous UUID validation of the assignment ID. Keep examples and import tests synchronized with the actual importer.
- [PIM request #1474](https://github.com/hashicorp/terraform-provider-azuread/issues/1474) was closed as requiring a separate API/resource. AzureAD's eligibility resource sends `adminAssign`/`adminRemove` schedule requests with schedule information; its special role/principal 404 retries and request-retention fallback belong to that lifecycle. [Eligibility implementation](https://github.com/hashicorp/terraform-provider-azuread/blob/e4bf321593a89f1363ef6ebe457f5843b8046882/internal/services/directoryroles/directory_role_eligibility_schedule_request_resource.go#L84-L216), [Graph beta eligibility requests](https://learn.microsoft.com/en-us/graph/api/rbacapplication-post-roleeligibilityschedulerequests?view=graph-rest-beta), [Graph beta assignment-schedule requests](https://learn.microsoft.com/en-us/graph/api/resources/unifiedroleassignmentschedulerequest?view=graph-rest-beta). Direct assignment is active access, not eligible access; do not add an `eligible` switch or scheduling fields here.

**Proposed microsoft365 design, not HashiCorp behavior:** implement the tenant-scope Framework resource with required `role_definition_id` and `principal_id`, UUID validation and replacement modifiers; computed opaque `id`; send `directoryScopeId: "/"` explicitly. No configurable app scope is necessary for ask 2. Use direct beta SDK POST/GET/DELETE calls inside CRUD with existing shared timeout/retry/conversion helpers. No stable fallback is needed. Make import consume the opaque Graph assignment ID consistently with repository convention, and document that choice independently of AzureAD's full-path format. Reject imported assignments outside tenant scope so replacement/deletion cannot unexpectedly manage an AU/application assignment. Treat item GET 404 as absent after create stabilization, and DELETE item 404 as already deleted; retain authentication/authorization errors. Preserve the created ID before any waiter failure. If duplicate discovery is added, return a concrete import ID for an exact role/principal/scope match rather than silently adopting it; verify any claimed duplicate status against a real response first. These are design recommendations based on the verified boundaries above, not claims that upstream already implements them.
